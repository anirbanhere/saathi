# Exact STT wire options and the remaining authority boundary

## Implemented scope

`compileVendorSttRequest(unknown)` in `vendor-stt-request.ts` validates a strict credential-free object and returns detached frozen endpoint/header-name/form-field/timeout metadata. The existing disabled Sarvam/ElevenLabs factories use this compiler to construct the request actually sent, after their existing enablement, key, consent, allowed-language and bounded WAV checks. No route, reader, account verifier, grant issuer, worker, schema migration or live request is added. Source15/public7 and existing profiles stay unchanged.

Accepted fields are provider/model, optional languageHint (the five existing locale labels or null/absent auto-detect), optional timeoutMs (1000..60000, default20000), and ElevenLabs-only providerLogging (deny/allow, defaultdeny). Model allowlists remain saaras:v3/v4 and scribe_v2. Explicit Sarvam logging intent is rejected because no matching retention-control parameter was verified. The compiler accepts no key, file/audio, arbitrary endpoint/header, source URL, token, webhook, transcript editing, keyterms, extra paid-feature fields or positive authorization metadata. Invalid values/property failures produce one fixed LocalError without serializing input.

Sarvam uses its fixed endpoint/header, model, language_code or unknown and with_timestamps=false; only v3 sends mode=transcribe. ElevenLabs uses its fixed endpoint/header, model_id, ISO hint when present and false diarization/events/webhook/multichannel plus no timestamps. Its query requests enable_logging=false unless the internal factory was explicitly configured allow. These are the same options as before this extraction. A logging/eligibility rejection never changes them or retries. The returned object contains neither keys nor audio and proves neither account provenance nor entitlement. It is not persisted or bound to a hold/grant in this slice.

## Primary-source review, 3 November 2026

- [Sarvam REST STT](https://docs.sarvam.ai/api-reference/speech-to-text/transcribe) documents multipart transcription, both reviewed models, language hints and timestamps. Its v4 model summary and v3-only mode description still differ; preserve the existing default-mode behavior, pending provider clarification. No retention switch was found in this reviewed request contract.
- [Sarvam authentication](https://docs.sarvam.ai/api-reference/authentication) uses api-subscription-key and documents403 for both missing/invalid keys and forbidden authenticated requests. HTTP403 alone cannot prove which condition occurred. Do not infer verified account identity from it.
- [Sarvam billing](https://docs.sarvam.ai/api/platform/billing) states credit sharing is organisation-wide across workspaces, keys and products. Future trusted accountRef mapping must represent that billing pool, not a newly invented per-key/workspace allowance. Existing synthetic journal labels are not evidence of that mapping. External clients can spend the same pool.
- [ElevenLabs transcription](https://elevenlabs.io/docs/api-reference/speech-to-text/convert) documents enable_logging=false as enterprise-only zero retention and additional-cost transcript editing. The compiler preserves the former request preference and excludes the latter. A requested flag is not proof of account eligibility or deletion.
- [ElevenLabs zero retention](https://elevenlabs.io/docs/eleven-api/resources/zero-retention-mode) describes selective enterprise eligibility and per-request behavior for supported products. It does not establish this project's entitlement. No current account was queried.
- [ElevenLabs user](https://elevenlabs.io/docs/api-reference/user/get) exposes user/workspace identity; [subscription](https://elevenlabs.io/docs/api-reference/user/subscription/get) exposes tier, character counters and overage settings. **Design inference:** those response fields alone do not prove STT-specific permission, retention eligibility or a currency-priced available STT balance. No conversion formula or positive grant is implemented from them.
- [ElevenLabs key permissions](https://elevenlabs.io/docs/help-center/technical/how-do-i-authorize-myself-using-an-api-key) describes feature restrictions and optional key credit caps. Future setup should preserve least privilege rather than turning restrictions off.

These are documentation findings, not authenticated account observations, current tariff approval, service availability or Indic speech-quality evidence. No API/credit/top-up/contact request occurred.

## Concrete admission design — proposed, not implemented

Default bootstrap continues to install none of the balance/role/access observers. `reviewAccess` remains a denial-only diagnostic and its requestOptionsBound=false context remains honest. Do not upgrade that status because a compiler object exists. No positive JSON/cache result, subscription tier, digest match or test fixture can mint authority.

Before any live issuer is implemented, the coordinator must choose an actual speech provider/account, acceptable retention behavior and separately authorize the narrow setup/probe. Keep interchangeable model/speech contracts; Sarvam/ElevenLabs wire support does not obligate the product to buy them. Fully self-hosted/open-weight speech remains an alternative requiring its own resource/quality design. Do not repeatedly request skipped Nous setup or reuse the consumed Meta test approval.

A bounded first integration can inspect explicitly selected account metadata only, using its own disabled-by-default operator command, fixed endpoint, server-held key, timeout/byte cap, no audio, redirects or automatic retry. Return only fixed blockers. For ElevenLabs GET user/subscription, validate and minimize identity/status/counter data; do not persist names, invoices or credentials. Restricted-key403 means unavailable verification, never permission to broaden scope. Sarvam's reviewed pages do not establish an authoritative machine-readable balance/identity endpoint; do not invent one or scrape its dashboard. Even a successful metadata probe cannot clear missing STT terms, retention or currency/balance evidence.

A future authoritative issuer requires all of the following **together**, with independently reviewed provenance: active owner/session and scoped processing consent; immutable new-hold policy/role plus exact compiled request options; server-mapped billing account/currency and credential generation; reviewed current tariff and bounded fresh account spend evidence; provider terms/retention eligibility for this endpoint and selected option; owner/model/language/duration/byte/spend scope and expiry/revocation identity. Bind the actual WAV hash and consent revision immediately before dispatch. Missing, stale, unbound or conflicting evidence denies. Never infer money from character counts or combine distinct account pools under convenient aliases.

The issuer must own a private non-serializable capability checked by its executor, independent of model/HTTP/client data and synthetic fixtures. Durable metadata alone does not authenticate that capability. Claim/dispatch needs a separately reviewed journal transition that prevents replay across restart/model changes; reserve before potential remote IO, record uncertainty before dispatch and retain possibly charged amounts after timeout/cancel/crash until authoritative reconciliation. Existing cancelled_unissued is valid only when dispatch was impossible. This compiler adds no such claim or dispatch path, and has no provider idempotency/status guarantee to justify automatic replay.

Acceptance before activation must cover forged/foreign/revoked/stale authority, role/options/account swaps, retention mismatch, insufficient credit, independent spend, concurrent owner/day/revision budgets, atomic failure, privacy revocation, unknown remote cost and restart recovery using fresh synthetic stores. A separately authorized bounded real synthetic probe and consented en/hi/ta critical-field evaluation are later evidence, never implied by mocked tests. Private/public rollout requires its own backup/upgrade and review.
