# Reviewed STT role and policy compatibility

`createSttRoleBinding(profile, role, tightenedLimits?)` is an isolated content/compatibility helper. It validates a candidate independent STT role against complete reviewed pricing/budget policy, returns deeply frozen metadata and `executionAllowed=false`, and grants no access or execution. It cannot attest that its input came from the actual runtime configuration; a future trusted caller must resolve and bind that provenance. Existing schema14 journal rows remain unbound. No migration, Store/claim wiring, registry, environment loading, credentials, balance reader, HTTP/model tool or provider call is added.

The role contract shares the existing Sarvam saaras:v3/v4 and ElevenLabs scribe_v2 wire allowlists, language schema and1000–60000ms timeout with the disabled vendor factories. Model/provider must exactly match the tariff, and every policy language must be covered by the role. Known extra role languages remain in the immutable identity but cannot widen policy admission. Current budget policy still limits language labels to en/hi/ta; ml/kn transport labels are not acceptance or language-quality evidence. Fixture/disabled/local-whisper and TTS model candidates are outside this priced vendor boundary.

The shared PCM/WAV byte limit is2,000,000 bytes, used by the wrapper, inspector, speech parser and vendor bounds. The compatibility check rejects a profile that permits more than that limit, including a2MiB ceiling, and preserves the vendor100ms–29s range. No silent clamping or policy rewriting occurs. A real profile correction requires separately reviewed catalogue content/revision, not reuse of an immutable old revision. Actual bytes, mono-channel admission, current consent/session, fresh tariff/balance and atomic budgets still require their existing runtime checks.

The versioned project recipe is `saathi-stt-role-binding-v1`, wrapping the policy's complete canonical content and a copied role with sorted unique language membership, model, provider and timeout. Fixed alphabetic wrapper/role keys plus canonical policy keys produce exact JSON bytes and SHA-256. This is a project format, not general JSON canonicalization or authentication. Different provider/model, role language set, timeout or effective narrowed ceilings change identity. Input key/set order and duplicate role language labels normalize consistently; extra credentials/options/purpose/approval fields deny with fixed reasons. A Python-generated reference fixture independently checks bytes/hash.

Historical tariffs can have compatibility identity. A match does not prove current pricing, vendor availability/credits, account rights, retention eligibility, actual speech quality, approval or a worker lease. Retention/request options, actual immutable runtime-role/account-grant provenance, durable association with a hold and one-shot worker ownership remain unbound prerequisites before dispatch. No future caller may treat this helper or a digest as that authority. Providing a matching binding and even a key still leaves the existing factory disabled without its separate gate; tests verify zero HTTP calls.

Verification uses only synthetic policy labels/prices, generated tones and mocked transports. It covers independent canonical evidence, deep immutability/input isolation, provider/model/media/language consistency, model switching, strict settings, throwing accessors, historical content and the disabled factory. Existing vendor wire/deadline/cancellation tests remain mandatory after factoring shared constraints. Source, CI and packed-build evidence belongs in HANDOFF.md. Private/public profiles, provider/spend guardrails and the public schema7 deployment are unchanged by this increment.
