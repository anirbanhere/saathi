# Optional durable STT role snapshots

Source15 adds an immutable `stt_hold_roles` child table for metadata associated atomically with newly created budget holds. Normal bootstrap supplies no `sttRoleReader` or balance reader. When an internal trusted caller deliberately supplies a synchronous role reader, it receives frozen owner/provider/account/policy labels and supplies the selected role, independently of tariff model strings. The existing compatibility helper validates and copies it before acquiring the write transaction. A configured reader failure/mismatch denies; it cannot silently fall back to unbound mode. Readers run outside the transaction so separate privacy actions cannot be rolled back with a failed hold.

Successful creation inserts both hold and complete role/policy JSON/digest in the same immediate transaction. Unknown snapshot guards or a failed second insert roll back the new hold and all its units. The only write path is new-hold creation; there is no retroactive association method or public route. Exact duplicates return the original snapshot/status without role or balance reads, even after role configuration changes. A new selected model needs a genuinely new request and consistent reviewed price/policy; existing request identity cannot be replayed or rewritten.

The scalar projection reports `roleBinding=recorded` or `unbound` and always `executionAllowed=false`. This distinguishes recorded local metadata from a live grant. A trusted injected reader is an application sourcing boundary, not cryptographic proof of runtime configuration, account ownership, vendor credits, current eligibility or retained-processing permission. Actual verified account/grant context, retention/request options, one-shot worker/claim authority and remote financial reconciliation are still absent. No provider/factory/HTTP/model tool, key loading or dispatch is enabled.

Missing role-reader configuration preserves the prior metadata-only hold mode, which remains execution-ineligible. Existing schema14 holds migrate with zero associations and stay unbound. Supplying a reader on restart or retry does not backfill them. New and old unbound holds can use the existing explicit unissued-cancellation path, retaining attempt/audio/lifetime history. Recorded snapshots remain immutable through cancellation, media revocation/deletion/expiry and restart; no role change, refund, replay or automatic release follows from those events. Caller authentication remains the enclosing exact-session/ownership boundary.

Reads rederive canonical role/policy identity against the owned hold's complete effective policy, original creation time and owner. Forged scope, bytes, digest, policy or timestamp yields a fixed storage error, never an unbound fallback or silent healing. No keys/audio/transcripts are stored in this table or returned in the status projection. The table references the immutable hold ID and has fixed update/delete rejection guards. This is integrity checking for the trusted application database, not protection against an administrator replacing it.

The additive migration creates only this table/guards and advances version in the existing transaction. Failed migration preserves the prior version/data and releases ownership. Current binaries can open source15; older binaries refuse it. Do not open existing private/public profiles to test: they require their own consistent backup/upgrade checkpoint. Operator maintenance accepts genuine11/12/13/14/15 only because its guarded media schema is unchanged; it never migrates or changes snapshots/hold states. Older test fixtures explicitly omit the future child table before reconstructing their historical format, rather than weakening production FK checks.

Fresh synthetic tests cover atomic creation, no client snapshot/role overrides, mismatch/no fallback, unsupported/thrown/async readers, duplicate identity, corrupt evidence, immutable rows, privacy changes outside transactions, cancellation/reopen, old14 no-backfill and failed15 migration. No live account/key/provider or current profile is involved. Exact source/gates/build evidence is in HANDOFF.md. The next execution boundary must establish verified grants and worker identity; `recorded` is not that authority.
