Source14 adds internal `cancelUnissued(owner, id)` for holds created under this runtime's never-dispatched journal contract. This releases a local estimate and pending slot; it is not a vendor refund, payment receipt, processing approval or provider cancellation. There is still no dispatch/worker/provider method, actual STT-role/account grant, verified balance service or HTTP/model tool. Normal bootstrap installs no balance reader. Existing private/public profiles remain unopened; public source27de098/schema7 is unchanged by development.

The enclosing service must authenticate the caller and resolve its owner context. The method checks the current active owner session, exact journal schema/guards and canonical original record inside an immediate transaction, then rechecks the decision clock/session after policy validation. Only held to cancelled_unissued is permitted. Repeat cancellation returns the original state/time, and retrying the original reserve request returns that terminal record without another observation or unit. A genuinely new request may reserve again only after current consent/media/balance/budget checks. No client proof, state, role or approval field is accepted. Metadata-only cancellation remains possible after media expiry/deletion and without a balance reader; it never reads audio or restarts processing.

Original media identity, complete default/effective policy pins, cost estimate, balance observation and creation time stay immutable. The projection retains estimateMicros, reports outstandingMicros=0 after cancellation and always executionAllowed=false. Only the confirmed unissued monetary hold is excluded from outstanding/daily-money counters. Hard5000 rows and exact owner/request history remain; cancellation is not eviction, a ledger reset or automatic expiry/refund. Other held rows survive restart and privacy maintenance unchanged.

Schema14 replaces the schema13 one-owner lifetime constraint with a unique held-owner partial index, preserving unique(owner,request). A guarded single transition plus coupled state/timestamp constraints prevents reopening, changing original fields, deletion, initially cancelled insertion or unsupported states. No remote-unknown state is supported by this contract. Future dispatch must add actual role/grant/worker identity, explicit never-dispatched versus possibly-charged states and provider-specific reconciliation before any IO; do not extend this cancellation method to release an unknown charge on timeout, restart or local acknowledgement.

The migration accepts only the exact known schema13 table/guards, bounded rows and no custom journal index. It refuses staging collisions and any incoming foreign key, matching SQLite identifier case rules, before replacing the table, so an unknown cascading child cannot lose rows. The existing ownership guard and immediate transaction cover create/copy/drop/rename, guard/index creation and affected foreign-key verification; version advances only with that transaction. All original columns are copied, with held/null initial lifecycle values reflecting schema13's no-dispatch contract. This is not proof of outside vendor activity. Failures preserve version/data and release ownership. Foreign-key enforcement and schema error checking stay enabled.

SQLite describes the [create/copy/drop/rename procedure](https://www.sqlite.org/lang_altertable.html#making_other_kinds_of_table_schema_changes) for removing UNIQUE constraints. Its [foreign-key rules for DROP](https://www.sqlite.org/foreignkeys.html#fk_schemacommands) explain why unknown incoming references must be refused: dropping can invoke cascading actions. Our narrower migration has no allowed incoming references and keeps enforcement on. Schema inspection uses parameterized [table-valued PRAGMA queries](https://www.sqlite.org/pragma.html#pragfunc), never model-provided identifiers or writable_schema.
