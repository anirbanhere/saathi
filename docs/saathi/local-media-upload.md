# Local WAV upload and initial consent

The development branch adds a local HTTP upload boundary. It does not add a file picker/recording UI, playback, transcription, task execution, model submission or public speech. Existing public/private profiles remain unchanged; do not enable this on an existing profile just to test development. Tests use fresh synthetic databases and generated PCM tones only.

`SAATHI_LOCAL_MEDIA_UPLOADS=false` is the default. Literal `true` enables uploads only on the loopback self-hosted runtime; configuration rejects public-origin mode, and route registration independently refuses public mode even with programmatic opt-in. The existing `SAATHI_LOCAL_MEDIA_CONTROLS` remains independent: enabling metadata/deletion does not enable upload. A new `/health` field `local_media_uploads` reports this boundary separately from `speech=false` and `actions=false`. Do not interpret an enabled upload flag as speech-provider or account authority.

`POST /api/media/upload` accepts a single raw PCM16 RIFF/WAVE body. It requires the current local session cookie, exact same origin, existing `X-Saathi-CSRF`, and exact `Content-Type: audio/wav`. Other methods/paths do not receive a binary exception. No query fields, multipart, URL, filename, local path, compressed body, client owner or provider selection is accepted. Header names are case insensitive; custom `X-Saathi-*` headers outside this contract are rejected.

| Header | Contract |
| --- | --- |
| X-Saathi-Request-ID | Required1–80 ASCII letters/digits/underscore/hyphen; persisted owner-scoped duplicate identity |
| X-Saathi-Consent-Store | Required exact `true`; storage consent is explicit |
| X-Saathi-Consent-Process | Optional exact `true`/`false`; omitted defaults to `false`. Records consent only, starts no processing |
| X-Saathi-Language | Optional configured language-code enum; a hint, not detected language or quality evidence |

The parent host/origin/method/rate/session/CSRF gates run before the application reads upload bytes. The route validates metadata and admits at most one concurrent buffer per owner/four per app. Its reader enforces2,000,000 bytes, a15-second total read timeout and client-abort cancellation. Declared overflow/invalid length and actual overflow return413; a completed body that disagrees with its declared length returns400. Reader failures return a fixed400, interrupted/timed-out reads408, and capacity/storage budgets429. Unsupported metadata or WAV input returns422. Early rejections do not ask the application reader to consume the body; the HTTP runtime can still receive/buffer transport data within its ceiling. No raw stream/SQLite payload is exposed.

The exact session is checked again after reading and before synchronous admission; another active session for that owner cannot rescue an expired cookie. Admission then reuses the owned-media WAV/consent/quota/history transaction. The response is owned metadata only, status200 for successful fresh or duplicate admission. Existing retention clamps, owner byte/clip/lifetime quotas and tombstones apply. Same ID with changed bytes/consent/language conflicts409; a matching deleted request returns its saved tombstone and cannot revive or regrant consent. No STT admission, usage-unit charge or model call is made by upload. An abort after a committed write/lost response is not proof of rollback; recover state or retry the same exact request ID rather than inventing a new one.

JSON mutations keep their60KB declared and streamed limits and existing authentication/error order. The native Bun transport ceiling stays60KB by default/public mode, rising to2MB only for the explicit local-upload profile; the application still applies60KB to every ordinary JSON mutation. This uses Hono's [raw Request](https://hono.dev/docs/api/request#raw) after its [ordered middleware](https://hono.dev/docs/guides/middleware#execution-order), and Bun's [maxRequestBodySize](https://bun.sh/reference/bun/Serve/Options). No unbounded form-data parser or codec dependency is added. WAV validation inspects bytes; unsupported codecs require a future reviewed transcoding boundary.

Cancellation, timeout, invalid data, stale sessions and history-write failures release in-memory buffer admission; uncommitted audio has no saved media row. Stored metadata/BLOB clearing remains the existing explicit owner deletion/revocation or [operator expiry maintenance](media-maintenance.md), not a background cleanup promise or secure WAL/backup erasure. A processing-consent flag is not an execution lease, actual provider budget, future consent regrant or guarantee that returned copies can be recalled.

Tests cover default/public denial, exact-session expiry during streaming, metadata/consent/ownership, pre-read guards, bounded reads, timeout/abort/capacity recovery, malformed input, quotas, duplicates/tombstones, rollback, persistence and a real loopback WAV larger than60KB while JSON stays limited. Packed public smoke asserts uploads unavailable. UI recording/upload/consent controls and real browser review follow separately; actual consented recordings, live providers, budgets/quality evaluation, identity and official WhatsApp remain gated. See HANDOFF for exact source/CI evidence.
