# Canonical speech policy content identity

This increment defines immutable complete-policy identity for the future reservation journal. `createSttPolicyPin(profile, tightenedLimits?)` validates the same strict, coherent budget profile and limit normalization used by the offline preview. It copies known fields, normalizes language membership as a sorted unique set, freezes the complete reviewed profile plus effective limits, and returns canonical JSON plus its SHA-256 digest. Missing enablement denies; malformed or widened limits return fixed denials. The pin builder itself grants no account access, consent or execution. Source12 now uses default pins in the separate internal metadata catalogue described in stt-policy-catalogue.md; this does not activate policies or reserve funds.

The versioned project-specific recipe wraps `format`, `profile` and `effectiveLimits`, with domain tag `saathi-stt-policy-pin-v1`, sorted object keys, validated safe integer JSON values and ordinary JSON string encoding. Only language membership is unordered; model/provider/revision/account/currency, reviewed ceilings and effective limits, freshness/media bounds and every tariff field are preserved. Missing/equal overrides normalize to the same limits; a genuine narrowing changes identity. This is not a claim to implement a general JSON canonicalization standard. A reference fixture/hash computed independently with Python guards accidental recipe drift.

Reordering keys or language membership must preserve identity. Changing content under the same revision label must change identity. The source12 internal default-policy catalogue enforces revision/content conflicts transactionally and retains complete canonical bytes/digest. Future reservation storage must bind effective pins and handle format/schema evolution explicitly. A digest proves content identity, not who authorized it; a caller can compute another digest. Neither a valid pin nor an `enabled` field grants access, reserves money or permits a provider call. Keep policy metadata out of user-facing receipts and never place credentials in it.

The durable catalogue should compare default pins (no overrides) when enforcing reviewed-profile revision uniqueness. Each reservation separately binds its effective pin, including any legitimate narrowing. This permits different owner/request ceilings under one unchanged reviewed profile while preventing the same reservation ID from silently changing its effective limits. A changed reviewed profile under the same revision remains a conflict. Both identities are obtained with this same recipe; neither is an authorization credential.

Tests require strict unknown-field/coherence rejection, key/set-order independence, changed-content separation, independent digest evidence, deep immutability, input-copy isolation, safe denials and canonical round-trip. The pin builder reads no existing profile or environment and uses synthetic policy data only. Continue tasks/stt-live-ledger-design.md for storage/revision conflicts and atomic reservation; fixture-only tables/claims remain unchanged.
