# Next slice: bounded local audio upload and initial consent

Proposed next increment after operator maintenance; not implemented or a public-rollout authorization. Reuse the tested media/WAV/consent/quota store and privacy UI. Work only on fresh synthetic databases/tones; preserve current private/public profiles and the contributor's separate WhatsApp branch.

First implement the local HTTP admission boundary, then a separate reviewed upload/consent UI. Do not couple upload to transcription, model submission, a task/action or live speech activation. Public mode and default configuration must have no upload route. Keep the existing privacy-controls opt-in distinct: enabling viewing/deletion must not silently enable uploads. Use a separately validated explicit local upload flag and independent app-level public denial.

The current parent middleware accepts same-origin JSON and enforces60KB for every mutation before owner/CSRF checks. Real bounded WAV uploads need a narrow transport contract; do not globally raise this limit or attach a route ahead of authentication/security checks. Design one exact upload path/method with same-origin/session/CSRF/rate/security protections before accepting its body, a hard encoded/decoded size ceiling, strict metadata/consent/request identity and cancellation on streaming overflow. Keep existing JSON routes/limits unchanged. Prefer a single bounded WAV body with tightly validated metadata headers over unconstrained multipart/parser dependencies. Review the contract against official Hono/Bun APIs before implementation.

Owner identity, expiry, storage paths and retention limits come from the server. Accept no client owner override, remote URL, filesystem path, arbitrary filename, provider, credentials or executor token. Storage consent must be explicit; processing consent is separate and never inferred from model selection. Defaults must deny processing. Initial grants are recorded through existing admission/history, not a new bypass or a regrant for an existing tombstone. Preserve request-ID duplicate/conflict behavior, active-session/expiry/quota checks and immutable terminal media states. Return owned metadata only; no audio/transcript/claim/hash projection. No download/playback, provider call or processing route in this increment.

Tests first: default/public denial including programmatic opt-in; owner/session/origin/CSRF failures before accepting bytes; existing JSON60KB unchanged; missing/false/invalid consent and unknown metadata; exact bounded supported WAV and MIME/RIFF disagreement; declared/streamed overflow and cancelled reader; quota limits; duplicate/conflict/delete/replay; foreign-owner isolation; persistence and atomic history rollback; sanitized errors and no external fetch. Packed public smoke must prove absence of upload capability. Run focused/server/frozen/format/audit/packed gates and exact-source Linux CI, recording the Windows baseline accurately.

The later UI must explain local retention and separate storage/processing choices before sending any bytes, handle rejection/cancel/retry without duplicate writes and show saved metadata/expiry/deletion honestly. Verify that UI on a fresh isolated real browser with synthetic files. Actual consented recordings, transcoding, live-provider admission/spend, speech evaluation and public/WhatsApp access remain separate gates. Do not turn on an existing profile to try this work.
